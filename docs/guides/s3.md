# S3 and the workspace

Every path in Alchemist goes through [cloudpathlib](https://cloudpathlib.drivendata.org), and every query goes through
DuckDB, so the same code runs on S3, on a laptop and in tests. Switching to S3 is a matter of settings.

## Use S3 for the workspace

```bash
export ALC_WORKSPACE=s3://alchemist-workspace
```

Each workspace, project, question and run then gets its own S3 prefix, used as its filesystem:

```text
s3://alchemist-workspace/
  workspaces/<workspace>/
    workspace.yaml
    projects/<project>/
      project.yaml
      knowledge/
      questions/<question-id>/
        question.yaml                # text, asker, scope, plan, status
        runs/<run-id>/
          manifest.json  findings.json  notebook.ipynb  SEALED
          inputs/  work/  figures/  report/  logs/
```

Question and run ids are ULIDs, so they sort by time. See [Run folder](../reference/run-folder.md) for what each file
holds. The bucket needs no object versioning.

## Register S3 datasets

Register datasets with `s3://` prefixes ([catalog admin guide](catalog-admin.md)). DuckDB reads them through its
`httpfs` extension, set up by the built-in `s3` storage backend plugin, with an S3 secret built from the environment: the AWS credential chain, or the run's own
credentials when it has them (below). No keys are written to code or the notebook.

Globs are expanded with cloudpathlib once per query, and each object's key, ETag, size and last-modified time is
recorded before the query runs on that explicit list.

## Per-run credentials

Set `ALC_RUN_ROLE_ARN` to give every run its own S3 credentials. When a plan is approved (and for each replay), the
credential broker assumes that role once for the run with an inline session policy that allows only:

| Allowed | On |
| --- | --- |
| `s3:GetObject`, `s3:ListBucket` | the registered prefixes of the datasets pinned for the run, which are only those of its plants |
| `s3:GetObject`, `s3:PutObject`, `s3:ListBucket` | the run's own folder |
| denied: `s3:PutObject`, `s3:DeleteObject` | the run's `SEALED` file |

The sandbox kernel gets these temporary keys and none of the process's own (profiles, container and instance
credentials are removed from its environment), so a query that names another plant's prefix fails at S3 even if it got
past the tool layer. A replay gets no lake access at all, since it reads only its own snapshots.

The session carries the user as its source identity and the tags `alc:run`, `alc:user` and `alc:workspace`, so
CloudTrail shows who read what for which run. The manifest records the role, session name, expiry and the SHA-256 of
the policy, and the policy itself is kept in `logs/session_policy.json`. The keys are never stored.

What the run role needs:

- **Permissions:** `s3:GetObject` and `s3:ListBucket` on the lake buckets, and `s3:GetObject`, `s3:PutObject` and
  `s3:ListBucket` on the workspace bucket. The session policy narrows this per run.
- **Trust:** the orchestrator's role, with `sts:AssumeRole`, `sts:TagSession` and `sts:SetSourceIdentity`.
- **Session length:** the broker asks for `ALC_RUN_CREDENTIAL_SECONDS` (default 3600). With role chaining (an ECS task
  role assuming the run role) AWS caps this at one hour, so analyses longer than that need a refresh, which is not built
  yet.

STS limits the size of a session policy. The broker drops prefixes already covered by a shorter one and refuses a run
whose policy is still too large; register datasets under fewer, broader prefixes if that happens.

Without `ALC_RUN_ROLE_ARN` (laptops, tests), the sandbox uses the process's own credentials, the manifest records
`"credentials": {"mode": "ambient"}`, and the access rules are enforced in the tool layer only.

## Sealing on S3

When a run ends, the kernel has already stopped and `SEALED` is written with a conditional put (`If-None-Match: *`), so
a run can be sealed only once and an existing `SEALED` is never overwritten. The run's credentials cannot write
`SEALED`, and anything changed or added after sealing is reported by `alchemist verify`. No Object Lock is needed.

## Local S3 (MinIO, moto, LocalStack)

Set the standard `AWS_ENDPOINT_URL_S3` (or `AWS_ENDPOINT_URL`). boto3, cloudpathlib and DuckDB all use it. To try the
demo on S3:

```bash
export ALC_HOME=$(mktemp -d) ALC_WORKSPACE=s3://alchemist-workspace
alchemist demo setup --lake s3://my-lake-bucket/alchemist-demo
alchemist demo run
```

`demo setup --lake` uploads the synthetic lake there and registers its datasets with those S3 prefixes. The test suite
does the same against a moto server (`tests/test_s3.py`), with the credential broker switched on.

## Images without internet

The sandbox has no internet in the target design, so DuckDB cannot download `httpfs` at run time. The Dockerfile
installs it at build time; `install httpfs` in the kernel is then a no-op.

## Other stores

The catalog database (`ALC_DB`) stays local in the MVP. The access file (`ALC_ACCESS`) and the knowledge root
(`ALC_KNOWLEDGE`) are read through cloudpathlib and may be `s3://` URIs.
